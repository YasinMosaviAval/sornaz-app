# تطبیق پنل وب و اپلیکیشن — ۲۰۲۶-۱۰-۱۵

مبنای بررسی، شاخهٔ وب پس از ادغام `c328baf` و کد واقعی `MobilePanelCatalog`، مسیرها، کنترلرها و صفحات Flutter است. انتقال وب و Flutter به سرور یا شاخهٔ انتشار در این مأموریت انجام نشده است.

## قرارداد و دامنه

اپلیکیشن از کاتالوگ مجاز `GET /api/sornaz/v1/panel` استفاده می‌کند. هر عملیات از مسیر `/panel/{section}/{operation}` به یک کنترلر ثبت‌شدهٔ فعلی وب می‌رسد. کنترل نشست Bearer، middleware مسیر وب و کنترل مالکیت سرویس برقرار می‌مانند. نام نقش یا شناسهٔ سازمان ارسالی کلاینت جای مجوز سرور را نمی‌گیرد.

کاتالوگ فعلی ۶۰ تعریف بخش دارد؛ همهٔ آن‌ها برای همهٔ کاربران نمایش داده نمی‌شوند و یک تعریف جزئیات برگه مخفی است. این تعداد، معیار تأیید همهٔ گردش‌های کاری روی دستگاه نیست.

| گروه | موارد بررسی‌شده |
|---|---|
| حساب و ارتباطات | مشخصات، حریم خصوصی، امنیت، تغییر تماس، اسناد، دستگاه‌ها، ادغام حساب، پشتیبان مجاز، گفتگو، پیام و اعلان |
| آموزش | شعبه و نوع آموزشی، استاد و کارکنان، هنرجو، کلاس و نوع/دستهٔ آن، درس و سطح، دوره، ترم و جلسه، لغو/جبرانی، حضور و غیاب |
| زمان و مالی | برنامهٔ سازمان/اعضا، استثنا، قوانین زمان‌بندی، تعطیلات، فاکتور و اقساط، پرداخت، اشتراک، امتیاز و گزارش |
| محتوا و دسترسی | نوشته، دسته، دیدگاه، رسانه، برگه، راهنما، کاربران، نقش‌ها، مجوزها، ترجمهٔ رابط |
| اطلاعات شخصی | گالری، درس، برنامه، امور مالی و تنظیمات شخصی، سوابق، نشان، جوایز، تحصیلات، گواهی، رویداد، نظرسنجی و آثار |

## اصلاحات این مرحله

- انتخاب نمایش نقش و مجوز در پنل آموزشگاه/شعبه (`panelVisible`).
- ذخیرهٔ مستقل نقش‌ها و دسترسی‌های مستقیم؛ تفکیک مجوزهای ناشی از نقش و حفظ مجوز مستقیم پوشیده‌شده با نقش. عملیات قدیمی `users/update` برای کلاینت قبلی محفوظ است.
- شناسایی نقش‌های `academy_branch_*` و مالکیت مستقیم آموزشگاه/شعبه در کاتالوگ موبایل.
- دسترسی کاربر عادی به سوابق خودش؛ تأیید وضعیت همچنان مدیریتی و تابع مجوز سرویس است.
- انتخاب آموزشگاه یا شعبه برای کلاس، ایجاد نوع کلاس از مسیر مجاز موجود و افزودن درس به فهرست.
- بخش‌های تأیید و نهایی‌کردن ثبت‌نام در انتظار، ایجاد گفتگوی هماهنگی، انتخاب مدرس/جلسه یا روز و ساعت شروع.
- نمایش درخواست‌های ثبت‌نام خود هنرجو و ویرایش درخواست تأییدنشده با کنترل مالکیت سمت سرور.
- مدیریت وضعیت تعطیلی توسط مدیر سایت و تنظیم برگزاری کلاس در تعطیلات برای آموزشگاه مجاز.
- دریافت ساعت‌های آزاد ترم و بازهٔ برنامهٔ هفتگی از همان API وب.
- مشاهدهٔ جزئیات نوشته و دریافت اطلاعات کامل قبل از ویرایش؛ مدیریت ترجمه‌های رابط برای مدیر مجاز.
- تنظیم وزن قلم و گردی گوشه‌های سایت، پیش‌پرکردن تنظیمات شخصی از مقدار اختصاصی/پیش‌فرض و حذف کلیدهای غیرتنظیمی از درخواست ذخیره.
- فیلتر محلی آموزشگاه/شعبه برای فهرست‌های سازمانی بدون درخواست شبکهٔ اضافی. این فیلتر صرفاً نمایشی است؛ مرز دسترسی در سرور برقرار می‌ماند.

## تفاوت مسیرها

مسیرهای HTML پنل/دیالوگ ثبت شعبه در اپلیکیشن باز نمی‌شوند؛ صفحات Native فعلی جای آن‌ها را می‌گیرند. ایجاد شعبه از عملیات فعلی `branches/create` و تغییر تماس از عملیات اختصاصی موبایل انجام می‌شود. مسیرهای `realtime-version` برای polling وب هستند؛ اپلیکیشن طبق معماری موجود از بازخوانی کنترل‌شده استفاده می‌کند. ابزارهای seed و حذف دادهٔ آزمایشی سایت در API تولید موبایل اضافه نشده‌اند.

## انتشار و بازگشت

فایل‌های اجرایی وب لازم برای این اصلاح: `Modules/Analytics/Services/MobilePanelCatalog.php`، `Modules/Analytics/Services/MobilePanelAccess.php`، `Modules/Analytics/Services/PersonalPanelDataService.php`، `Modules/Analytics/Controllers/Web/PersonalPanelDataController.php` و `Modules/Analytics/Routes/routes.php`. کلاس، پکیج یا migration جدید لازم نیست. تست‌های وب در `scripts/mobile_panel_parity_test.php` و `scripts/mobile_panel_test.php --api-only` هستند.

ابتدا سرویس و کنترلر، سپس مسیر جدید و در پایان کاتالوگ و تشخیص دسترسی با حفظ تنظیمات محیطی منتشر شوند و تست API با حساب‌های آزمایشی بررسی شود؛ سپس نسخهٔ جدید اپلیکیشن توزیع شود. افزودنی‌های کاتالوگ با عملیات قدیمی سازگارند. برای بازگشت، نسخهٔ قبلی همین پنج فایل را بازگردانید؛ دادهٔ دیتابیس در این مرحله مهاجرت نمی‌کند. پس از بازگشت وب، بخش‌های تازهٔ کلاینت به کاتالوگ دریافتی وابسته‌اند.

## مرز اعتبارسنجی

تست قرارداد مسیرهای ثبت‌شده، تست Bearer با کنترلر واقعی و سرویس fixture، آزمون‌های مرز دسترسی و تست رابط Flutter اجرا می‌شوند. این آزمون‌ها جای اجرای نوشتنی روی MySQL تست، بررسی درگاه/پیامک و آزمون Android با حساب‌های واقعی هر نقش را نمی‌گیرند. بدون آن بررسی‌ها نباید برابری کامل عملیاتی یا آمادگی انتشار را قطعی اعلام کرد.

سناریوی دستی لازم: کاربر عادی فقط اطلاعات خودش، مدیر شعبه فقط شعبهٔ مجاز، مدیر آموزشگاه شعبه‌ها و خود آموزشگاه، و مدیر سایت تنظیمات سراسری را ببیند؛ درخواست شناسهٔ سازمان یا کاربر دیگر رد شود. تأیید ثبت‌نام، صدور فاکتور، پرداخت و لغو جلسه فقط روی دادهٔ آزمایشی انجام شوند.

## نتیجهٔ آزمون این تغییر

۵۳ تست مرتبط پنل، ناوبری، شعبه و حساب آموزشگاهی موفق شدند؛ هفت تست تازه نیز پس از آخرین تغییر دوباره موفق شدند. تحلیل پنج فایل درگیر بدون خطا یا هشدار و با ۱۴ پیام اطلاع‌رسانی قدیمیِ سبک کدنویسی پایان یافت (`--no-fatal-infos`). هفت مجموعهٔ PHP برای قرارداد مسیرها، نشست Bearer، ذخیرهٔ مستقل دسترسی، اطلاعات شخصی، مرز مالکیت و داده‌های SQLite موفق شدند؛ مجموعهٔ tenant شامل ۱۴۱ بررسی بود.

در اجرای گسترده‌تر، سه تست قدیمی اندازهٔ عنوان حساب، مقدار قدیمی ۲۰dp را به‌جای استاندارد ۱۴dp انتظار داشتند و شکست خوردند؛ کد عنوان در این مأموریت تغییر نکرد. دو fixture قدیمی قالب وب نیز مشکل مستقل دارند که در راهنمای انتشار وب ثبت شده است. بررسی نگهداری PHP برای متدهای جدید موفق بود، اما کل بررسی به‌دلیل متدهای بزرگ قدیمیِ خارج از این اصلاح هنوز موفق نیست. این موارد پنهان نشده‌اند و آزمون کامل انتشار، دستگاه واقعی یا سرور اصلی تأیید نشده است.

این تغییر وابستگی تازه‌ای ندارد و به OMR یا تحلیل اجرای آزمایشی وابسته نیست. انتقال به Release باید انتخابی باشد و دستورالعمل اختصاصی آن Worktree حفظ شود.
